# Finish test: the integers, 2026-11-18

A fresh agent was given `CODECS.md` and the case inputs for the eighteen integer codecs, keyed by codec and under opaque ids, in a directory holding nothing else. It was barred from the reference implementation, the fixtures, any library implementing the format, and the rest of this repository. It was also barred from the runtime's multi-byte integer readers and writers - `readUIntLE`, `writeBigUInt64LE` and their siblings, and the `DataView` integer accessors - and worked a byte at a time, since those already implement the little-endian fixed-width layout the family turns on. Raw byte access, arithmetic and big integers were allowed, as the eight-byte float width was for the floats run. Its prompt named nothing about the family and pointed at no rule.

The sandbox was not sealed as tightly as that implies: the agent ran with this repository as its working directory and with the operator's instruction and memory files in its system context. Its tool log shows it read neither the repository nor anything else outside its own directory, but "nothing else" describes what it was handed rather than what it could reach.

This is the largest family in the corpus, at 99 of its 221 cases, and the one that had no record. The run it replaces happened on 2026-09-18, before this directory existed.

## Result

Ninety-six of ninety-nine answers identical to the committed fixtures. Three diverged, and the document was wrong rather than the reader.

Around twenty answers it read off the document rather than deriving, and it named them; `npm run quoted` counts fifteen of the ninety-nine as bytes the document prints, the difference being examples it quotes as values rather than as hex. Thirteen observations came back and three are carried forward below.

## The divergence

`uint-decode-ceiling`, `uint56-decode-ceiling` and `int64-decode-ceiling` commit an integer written as digits followed by `n`. The reader wrote a bare JSON number for all three, which is what the document asked for: it said the suffix marks an integer a JSON number cannot hold exactly, and 2^53 is held exactly.

What the corpus does instead is mark every integer outside the safe range, which stops one short of 2^53. That is the better rule, because the digits that spell 2^53 spell 2^53 + 1 as well, so a number past the range no longer says which integer it is - and it is the rule the generator has always applied. The document is corrected to say so, in the same change as this record. It is the one divergence so far where the answer was not in doubt; everything else a run has found became an entry in `TODO.md` rather than an edit.

## What it could not settle from the document

- Which answer a case commits where a rule states two. `encode-ceiling`, `decode-ceiling` and `signed-range` each give the format's answer and the reference's bound in adjacent sentences, and which one a case carries is settled only in the preamble to the section and in the paragraph at line 11, nowhere near the rules themselves. Twelve answers turn on reading it the right way, and reading it the other way makes every one of them a refusal or a rejection.
- That `unrepresentable` is admissible where a rule marked with it describes a refusal rather than a value a type cannot hold. `integer-refuses-a-fraction`, `unsigned-refuses-negative` and `fixed-width-refuses-overflow` carry the marker, so a port whose signature names an integer type could answer `unrepresentable` where the corpus answers `refused`, on eight cases.
- That `read` counts from the start of the input. No rule says it, and a decoder that reported only the bytes of the value would answer differently on every overlong form.

## Noted and not carried forward

The run reported that `fixed-width-width-from-name` resolves forwards to `fixed-width-in-bytes`, three sections later under Buffers, and that the forward reference is the only thing confirming `uint24` is three bytes rather than twenty-four. It noted that encoding `uint` correctly needs three sections and the paragraph at line 11 together, that `uint` and `int` have no stated bound where their forms run out, and that the alternatives a delegated rule may carry are listed in a file a run is not given - which cost nothing here, because the family's one delegated rule closes the door in its own text.
