# Finish test: the strings, 2026-11-17

A fresh agent was given `CODECS.md` and a list of case inputs, in a directory holding nothing else. It was barred from reading the reference implementation, the fixtures, any library implementing the format, and the rest of this repository. It implemented `utf8` in plain JavaScript from the document, answered all 22 cases of the utf8 directory, and reported where the document left it guessing.

It was also barred from the runtime's own UTF-8 encoder and decoder - `Buffer.from(s, 'utf8')`, `toString('utf8')`, `TextEncoder` and `TextDecoder` - and wrote the byte level itself. Those already implement the substitution this family turns on, so a run that leaned on them would check the runtime against the fixtures rather than the document.

## Result

Twenty-two of twenty-two answers identical to the committed fixtures, including every case the substitution rules exist to separate: `ed a0 80` as three replacements, `f4 90 80 80` as four, `e1 80 61` as one replacement and `a` against `e0 80 41` as two and `A`, and an unpaired surrogate announcing a count of three.

## What it could not settle from the document

Each of these became an entry in `TODO.md` rather than an edit to either side.

- Which byte sequences are well formed. The document delegates that to RFC 3629 and restates none of it, and four cases turn on the restricted ranges a lead byte allows behind it. A port that knows UTF-8 but not those ranges writes the decoder where any continuation byte continues any lead, and answers one replacement for `ed a0 80` where the corpus says three. The rules do determine the answer between them, but only to a reader who already holds the table.
- How many replacements each example in `utf8-invalid-forms` becomes. The rule names three sequences and ends "a decoder that returns any of the three rather than replacements disagrees with the reference" - a plural covering the three collectively rather than a count for each. The run answered two, three and four; reading each sequence as one invalid form worth one replacement is as available, and all three are live cases.
- What `utf8-maximal-subpart` does with a byte that cannot begin a sequence. A run is the longest prefix that could still have been completed, and for a stranded continuation byte that prefix is empty, so the rule as written leaves a decoder making no progress. The `e0 80 41` example forces one replacement per such byte where one is stranded alone, and says nothing about several in a row.
- What `f0 80 80 80` decodes to. It appears in no rule and no example, and admits one, two or four replacements under three readings of the rules that do exist.

## Noted and not carried forward

The run reported three smaller silences, each of which it resolved from rules that are stated: `utf8-replaces-unpaired-surrogate` says "an unpaired surrogate" where "each unpaired code unit" is what the cases show; a truncated count is covered by `uint-truncated-rejected` and named by neither utf8 rejection rule; and a `decodes` answer is never said to use the `units` form, which cannot arise for this codec because every invalid byte becomes U+FFFD.

It also observed that the cases write values as `units` where the units all pair, which is broader than the trigger the document states for that notation, and that the count rules a reader needs are in the uint section rather than this one. Neither changed an answer.

## Method

The run is reproducible: copy `CODECS.md` and the `input` fields of the cases to an empty directory, and give an agent with no other context those two files, barring it from the runtime's own UTF-8 encoder and decoder.
