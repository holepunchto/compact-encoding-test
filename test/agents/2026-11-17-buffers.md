# Finish test: the buffers, 2026-11-17

A fresh agent was given `CODECS.md` and a list of case inputs, in a directory holding nothing else. It was barred from reading the reference implementation, the fixtures, any library implementing the format, and the rest of this repository. It implemented `buffer`, `optionalBuffer`, `raw`, `uint8array` and the six fixed widths in plain JavaScript from the document, answered all 30 cases of the ten buffer directories, and reported where the document left it guessing.

The cases were handed over keyed by codec rather than in one flat list, because `fixed(3)` and `fixed(8)` differ only in the width they were built with, which a flat list does not carry. That is what a directory per codec gives a reader of the corpus itself. No runtime primitive was barred; the family needs none beyond raw byte containers.

The run was not sealed as tightly as that sentence implies: the agent ran with this repository as its working directory and with the operator's instruction and memory files in its system context, one of which names this project and states what the `unrepresentable` marker covers. Its tool log shows it read neither the repository nor anything else outside its own directory, but "nothing else" describes what it was handed rather than what it could reach.

The prompt steered the run: it named "two things this family turns on, so read for them deliberately: what a decoder hands back and how an answer should say so, and the places where two codecs write the same bytes and are told apart by something other than the bytes". The second half points at `optionalBuffer`, which the run independently called the clearest rule in the family, so the steer landed where it was least needed - but the record describes a run that was given it.

## Result

Thirty of thirty answers identical to the committed fixtures, including the pair the bytes cannot tell apart: `optionalBuffer` writing `00` for an absent value and for an empty buffer, which the run got right in both directions.

`uint8array` writing what `buffer` writes is not a second such pair. Those cases discriminate nothing, because both codecs answer as hex and no answer names a container, so a port handing back the wrong one passes them. Nine observations came back and four are carried forward below.

## What it could not settle from the document

Each of these became an entry in `TODO.md` rather than an edit to either side.

- Which rule `buffer-count-past-the-ceiling` answers to. `decode-ceiling` is marked `unrepresentable` and would let a port whose count type is a double answer that; `buffer-rejects-short-input` says the rejection holds "whether or not an implementation can read the count". Both reach a rejection, so the answer is safe and the admissible set is not. The run read the count as a big integer so that its rejection came from the input rather than from its own ceiling.
- What "a fixed codec carries a width its name announces" means for a codec the factory built. `fixed(3)` has no name, so the phrase fits only the pre-built exports, and the run went back to check whether `fixed-3` meant something other than `fixed(3)`.
- That no buffer case carries a count past `0xfd`. The arrays section gets a worked example of a count crossing the uint thresholds; the buffer directories get none, so the interaction of `buffer-count-then-bytes` with those thresholds goes unchecked here.

Two further gaps it found are the same ones earlier runs carried forward, and were added as sub-items there rather than as new entries: nothing in the Buffers section says what a `fixed` decoder does with too few bytes, which is the gap the floats run found in its own section; and the case of hex is still nowhere stated, which a second independent reader has now guessed from the examples.

The run also could not settle what a port reads to tell `buffer` from `uint8array`, since both answer as hex and nothing in a case names the container, and it proposed two remedies: tag the kind in the answer, or say in the document that the difference is untested. It was carried forward as an entry and then withdrawn after review, on the ground that the two codecs are distinct only because Node provided `Buffer` before `Uint8Array` existed, and an implementation without that distinction treats them as identical. That answers the first remedy. It leaves the second open, and `TODO.md` carries it: a reader is still told the two differ in what a decoder hands back, and is nowhere told that no case checks it.

## Noted and not carried forward

The run inferred three answers it could not read directly and reported each: a `read` of zero for a decode that took nothing, an empty `hex` for an encode that produced nothing, and a `read` of one for the absent `optionalBuffer`. Each is assembled from rules that are stated, and each came out right. It also noted that the bits-or-bytes question for `fixed` resolves forwards - the integer section points 45 lines on to `fixed-width-in-bytes` - and that the answer shape and the kind a decoded buffer carries both live in the front matter rather than in the section a reader goes to first.

## Method

The run is reproducible: copy `CODECS.md` and the `input` fields of the cases, keyed by codec, to an empty directory, and give an agent those two files and the steer quoted above. Reproducing it without the steer is a different experiment and should be expected to report differently.
