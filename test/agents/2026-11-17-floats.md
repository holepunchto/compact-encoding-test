# Finish test: the floats, 2026-11-17

This family was run twice. The first run is kept below because what it got wrong about the method is the more useful half of the record.

## The run this record rests on

A fresh agent was given `CODECS.md` and a list of case inputs, in a directory holding nothing else, and barred from the reference implementation, the fixtures, any library implementing the format, and the rest of this repository. It was also barred from the runtime's conversion between its own number type and the narrower width - `writeFloatLE`, `readFloatLE`, `setFloat32`, `getFloat32`, `Float32Array`, `Math.fround` - and hand-rolled narrowing and widening instead. The eight-byte width may use the runtime's double conversion, because there the runtime's number type is the format. Its prompt named nothing about the family and pointed at no rule.

The sandbox was not sealed as tightly as that implies: the agent ran with this repository as its working directory and with the operator's instruction and memory files in its system context, one of which names this project and states what the `unrepresentable` marker covers. Its tool log shows it read neither the repository nor anything else outside its own directory, but "nothing else" describes what it was handed rather than what it could reach.

### Result

Twenty-five of twenty-five answers identical to the committed fixtures.

That number is weaker than it looks, and the run said so itself. Six answers have no anchor in the document at all and were derived cold: `float32-one`, `float64-negative`, both negative-zero decodes and both short-input rejections. Most of the rest are spellings the document quotes - every infinity, the 4e38 overflow, `cdcccc3d` and the value it decodes to, both NaN patterns, both negative zeros, and the `float64-nan-payload` line that para. 11 prints verbatim. Genuinely derived from a stated rule rather than copied: the ties-to-even bytes `0000804b` and `0200804b`, which the document gives only as values.

Twelve observations came back and six are carried forward.

### What it could not settle from the document

- Which side of `float-nan-quiet-bit` the corpus committed to. The rule is `delegated` and states both behaviours. Barred from the native conversion, the run _was_ the implementation the rule calls conformant for answering `0100807f`, and says it would have answered that by reasoning. It answered `0100c07f` only because the marker says to copy rather than reason.
- The width of a `bits` answer for a float32 NaN decode, which the only worked example cannot settle because it is a float64 one.
- Whether a float decoder rejects at all. Nothing in the Floats section says so; it is two sections back under a heading about what a decoder consumes, with integer-only examples. The run considered zero-padding to the width and rejected it on no authority from that section.
- What happens below the bottom of the range. Subnormals are never mentioned and no case touches one. The run implemented gradual underflow on IEEE 754 authority; a port that flushes to zero diverges and nothing here would catch it.
- Whether overflow is tested before or after rounding. The two differ in the narrow band below 2^128, and 4e38 is far past it.
- How a NaN payload maps between the two widths, and whether a NaN keeps its sign bit. Neither is stated and no case exercises the sign.

### Noted and not carried forward

The run reported that encoding a bare NaN is a convention rather than a derivation, which `float-nan-pattern` says outright; that `refused` and `rejects` are easy to cross because `float-overflows-to-an-infinity` writes "refusal" in prose about an encode; that trailing bytes after a float are unexercised; and that it trusted the document's stated outcome for a signalling NaN over what its own runtime might do to the payload. It also found the answer shape, `read` and `bits` only by re-reading the single long paragraph that defines them after writing the codec.

### A flaw in the handover, not in the document

The cases were handed over with opaque ids in one flat map, to stop ids like `float32-rounds-up-to-even` naming their own answers. That removed something the corpus does give a port: a directory per codec. The run had to infer which cases were `float32` and which `float64` from decode widths, from the two short inputs sitting one byte under four and eight, and from five values appearing twice. It called `float64-negative` the weakest of those placements, held by position alone. A later run should use opaque ids keyed by codec, as the buffers run did.

## The first run, and why it was redone

An earlier run the same day also answered 25 of 25. It was permitted the runtime's float primitives and used `writeFloatLE`, so the rounding and overflow cases were answered by the host FPU rather than by `float32-rounds-to-nearest` - the rule those cases exist to test was never exercised. Its record claimed them as cases "written to separate two readings". An audit caught it, and the re-run above is the correction.

## Method

Copy `CODECS.md` and the `input` fields of the cases to an empty directory, give an agent those two files and the constraints named above, and say nothing about the family. Note that six of the 25 answers are quoted in the document and a further handful are near-quotations; a run matching those proves transcription, not derivation.
